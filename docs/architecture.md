# 基于事件溯源与 CQRS 的数字货币交易所架构设计

本设计将订单流转严格解耦为“定序与撮合、异步事件分发、异步持久化与投影”三个物理隔离的阶段，使关系型数据库不再出现在核心并发链路中。

## 0. 设计原则

* **单一事实来源：** Aeron Cluster 的 Raft Log 是系统唯一的事实来源，其他一切（Kafka 事件、MySQL、ES、行情）都是它的派生物。
* **确定性：** 撮合状态机对同一份日志重放必须得到完全相同的结果，这是快照恢复、稽核和主备一致的前提。
* **可以慢，不能丢（最高优先级）：** 延迟和吞吐可以为数据完整性让步，任何数据都不允许无声消失。落到具体机制，按优先级：
  1. **先持久、再确认：** 命令必须先写入日志并 fsync、被多数派接受，才能被认为已接受。
  2. **背压优先于丢弃：** 下游慢时，上游等待（变慢），而不是丢。撮合线程在**有界时间**内等待事件发布缓冲，而不是立即丢弃。
  3. **不能等的地方必须“可恢复”：** 让一个慢客户端拖住整个撮合是不可接受的（拒绝服务），所以回报通道（egress）允许丢；但结果必须能由**幂等重试取回**（见 §1），用户永远能查到自己的订单结果。
  4. **任何丢弃都必须可检测、可补回：** 靠事件序号发现缺口，靠 Raft 日志确定性重放补回；有计数和告警；检测必须有**定时任务**兜底，不能依赖“后面还有新事件”。
  5. **禁止静默：** 没有因未捕获异常而静默退出的线程，没有被忽略的错误返回值，没有不带回调的“发了就忘”。
* **服务可以挂，但不能出错（fail-stop，与上一条同级）：** 一致性优先于可用性。任何无法证明正确的状态，立刻停下，不继续对外服务；停机不会丢数据（日志还在），只是不可用。两条原则冲突时，先保证不出错，再谈不丢与低延迟。落到机制：
  1. **先校验、后改状态：** 输入在边界处校验；算术上界在改状态之前由输入约束保证（总供应量上限、价格/数量上限），而不是事后发现。
  2. **不变量检查与受检算术：** 所有金额运算用受检算术；每条命令处理完后，对被触及的账户检查余额非负。违反即视为程序缺陷，fail-stop。
  3. **状态机内不允许“吞异常继续”：** Agrona 的 AgentRunner 会记录异常后继续下一轮循环，而该命令的日志位置已经前移，状态可能只改了一半，而且所有副本会确定性地一起错。任何异常或 Error 都必须停机。
  4. **数据完整性：** 快照带魔数、格式版本、长度与校验和，不合格拒绝加载；Archive 对录制与重放启用 CRC32C，静默位翻转在重放时被发现而不是产生另一份“看起来合法”的命令。
  5. **版本：** 状态机有显式版本号（`appVersion`）。行为变化必须升版本，不兼容的版本拒绝加载旧快照/日志，而不是用新逻辑重放旧日志得到不同的状态。
  6. **副本一致性与重放校验：** 状态机维护一个对全部输出事件的链式哈希；每 N 条命令把检查点（序号 + 哈希）作为服务消息写入 Raft 日志。任何重放（重启、follower、补数）在到达检查点时必须得到同一个值，否则 fail-stop。这同时覆盖：副本分歧、日志损坏、新旧代码语义不一致。
  7. **下游写库前校验：** 投影表带 CHECK 约束（余额非负、剩余量在合法范围）；违反约束是**不可重试**错误，投影停下并告警，而不是重试或写入错误数据。
  8. **停机之后：** 由确定性日志触发的停机（“毒命令”）重启后会再次触发，这是预期行为：不能自动跳过那条命令（跳过就会与其他副本分歧），必须人工修复代码后重放。
* **撮合线程的热路径无锁、无数据库查询：** 日志落盘、快照、归档由 Aeron 的独立线程/进程完成。热路径唯一允许的等待是上面第 2 条的有界背压等待，并且等待期间必须持续让出心跳（`cluster.idleStrategy().idle()`），否则会被判定服务失联。
* **先冻结后撮合：** 资金校验与冻结发生在撮合之前、撮合集群之内，不能延后到下游投影。

## 1. 统一网关层 (Gateway)

* **极速接入：** 用户下单、撤单请求经网关完成鉴权、限流、协议编解码后，不走传统微服务 RPC，直接以定长二进制消息提交到 Aeron Cluster（目标编码为 SBE；骨架阶段使用等价的手写定长小端布局，见 §8）。
* **幂等与防重：** 每个请求携带 `clientOrderId`，由集群内状态机去重，网关重试不会产生重复订单。
* **超时重试是必须的：** leader 宕机时，已写入其 Aeron 发布缓冲但尚未被日志接收的命令会丢失，客户端/网关必须在超时后用同一 `clientOrderId` 重试；重试可能得到 `REJECTED(DUPLICATE_CLIENT_ORDER)`，表示首次已生效。
* **响应路径：** 集群对请求的确认（接受/拒绝）通过 Aeron egress 返回网关，再回传用户；成交与委托簿变动通过事件异步下发，不阻塞下单确认。
* **egress 允许丢，但结果必须能取回：** 回报通道到慢客户端不能让撮合等待，所以背压时回报会被丢弃（有计数）。为了“不丢结果”，请求必须幂等且**重试会返回原结果**：
  * 下单：状态机记住每个 `(account, clientOrderId)` 的结果（接受则记订单号，被拒则记原因）。重试同一 `clientOrderId` 得到 `REJECTED(DUPLICATE_CLIENT_ORDER)`，其中 `orderId` 是原订单号（原本被拒则为 0）、`price` 字段是原拒绝原因（原本被接受则为 0）。资金不足被拒的订单同样占用 `clientOrderId`，重试得到原拒绝原因，而不是重新校验。
  * 撤单：状态机记住已撤单的结果，重复撤单得到 `REJECTED(DUPLICATE_CANCEL)`，`orderId` 是原订单号、`price` 字段是原撤销的剩余数量。
  * 入金：必须带幂等键 `depositId`（每账户内唯一，> 0），没有键的入金被拒绝。重试同一笔得到 `REJECTED(DUPLICATE_DEPOSIT)`（`price` 字段是原金额），**不会重复入账**。“超时必须重试”与“入金不能重复入账”必须同时成立，所以入金幂等不是可选项；真实的入金/钱包服务必须用自己的流水号作为 `depositId`。
  * 这些“重复”回复是 REJECTED 事件，投影对其无状态变化，因此重试永远不会重复扣/释放资金。
  * 网关给在途请求设超时，超时后用同一 `clientOrderId` 重试。`clientOrderId` 必须由**用户/上游**生成，在网关重启后保持稳定，不能由网关生成。压测里不带超时的在途窗口曾在丢一条回报后永久卡死。
* **用户不直接连集群：** 每个集群会话在客户端和驱动里要占用 UDP 发布/订阅与缓冲（实测约 4 个文件描述符/会话），建立速度随会话数恶化（见 §5.1）。1 万并发用户由少量网关会话复用（几个到几十个），不是 1 万个集群会话。ConsensusModule 的 `maxConcurrentSessions` 默认只有 10，必须按网关数量显式配置（节点默认 1000）。

## 2. 定序与撮合层 (Sequencing & Matching)

> 注意：定序与撮合在同一个 Aeron Cluster 内完成。撮合引擎实现为 `ClusteredService`，在每个节点上确定性地回放 Raft Log，**不是**定序之后再通过网络交给外部消费者的独立进程，否则会多一跳网络并丢失 Raft 带来的高可用。

* **内存共识：** Aeron Cluster 通过 Raft 协议将并发请求转化为全局唯一的有序事件流（Raft Log），多数节点持久化后才提交。
* **单线程状态机：** 每个节点上，业务单线程按日志顺序依次执行：风控校验 → 资金冻结 → 价格时间优先撮合 → 生成事件。
* **订单簿数据结构：** 价格层使用红黑树/跳表或数组分桶，同价位内使用链表/环形队列维持时间优先。
* **无锁计算：** 撮合线程内无互斥锁、无网络等待、无数据库查询；输出事件写入 Aeron IPC 流（即该无锁环形队列的实现，单次 offer、不自旋），由独立线程发布。
* **事件序号：** 全局递增的 `eventSeq`（以及 `orderId`）由状态机自己分配，属于状态机状态并随快照持久化，因此对同一份日志重放得到的序号完全一致。它是下游去重和缺口检测的唯一依据。
* **发布规则：** 只有 leader 向外发布事件和 egress 回报；follower 与日志重放阶段只推进状态、不发布。**事件发布缓冲背压时先有界等待**（默认 3 秒，期间 `cluster.idle()` 保持心跳）；`ADMIN_ACTION`（缓冲轮转）立即重试；等待超时才丢弃并计数，丢弃的事件由日志补回（§3）。egress 回报不等待（理由见 §1）。
* **确定性约束：** 禁止使用系统时间（用日志时间戳）、随机数、无序集合迭代、浮点运算（金额一律使用定点整数）。
* **快照与恢复：** 定期对状态机做快照；节点故障后通过“快照 + 重放日志”恢复。需明确 RTO 目标并定期演练。

### 2.1 账户与资金状态

* 账户可用余额、冻结额作为撮合状态的一部分保存在集群内存中，下单时同步校验、冻结，撤单/成交时释放/结算，从而杜绝超卖与透支。
* 下游 Flink 负责对账、投影与审计，**不**承担下单前的资金判断。

### 2.2 多分区扩展 (Multi-Raft) 与跨分片资金一致性

按交易对切分到独立 Raft 组（如 BTC/JPY 与 ETH/JPY）可线性扩展吞吐，但同一账户会在多个分片挂单并共享同一份余额。可选方案：

| 方案 | 做法 | 优点 | 代价 |
|------|------|------|------|
| A. 额度预分配 | 账户资金按分片切片，各分片仅使用自己的额度，定期再平衡 | 撮合路径无跨分片调用 | 额度碎片化，需再平衡机制 |
| B. 独立资金分片 | 按账户分片的资金集群负责冻结/结算，撮合分片通过消息与之交互 | 余额强一致 | 下单多一跳，延迟与复杂度上升 |
| C. 按币种计价域合并 | 共享同一计价资产的交易对放同一分片 | 实现最简单 | 热点分片，扩展性受限 |

建议：初期用 C 或 A 起步，随规模演进到 B；该决策需单独设计评审。

## 3. 事件总线层 (Event Bus)

* **异步发布：** 状态机产出的委托簿变动、成交明细、资金变动等不可变事件，由独立发布线程投递到 Apache Kafka。
* **物理隔离：** Kafka 将对微秒级延迟敏感的撮合核心与下游毫秒级以上的持久化存储隔离。
* **投递语义（至少一次 + 序号去重 + 缺口补数）：**
  * 每个事件携带状态机分配的 `eventSeq`，同一交易对的事件固定写入同一 partition，保证分区内有序；Producer 使用幂等重试（`enable.idempotence=true`、`acks=all`）。
  * 重复与缺口**只能由消费端判断**：Flink 在 checkpoint 状态里保存 `lastSeq`，遇到 `seq <= lastSeq` 丢弃，遇到 `seq > lastSeq + 1` 视为缺口。发布进程内的去重器只是尽力过滤，重启后状态清零，不能作为缺口检测依据。
  * **事件发布线程不能静默失败也不能丢：** 按批取出事件，发送到下游并**确认成功**（Kafka 为 `flush` 且无失败回调）后才继续取下一批；失败则对同一批退避重试（至少一次，消费端按序号去重）。这期间发布缓冲逐渐填满，反压到撮合线程（变慢，§2），而不是丢。Kafka 生产者配置无限重试与无限发送超时，只有不可重试的错误才会抛出，抛出后同样进入重试而不是让线程退出。
  * **缺口检测必须有定时任务：** 消费端除了在收到事件时检查序号，还要在空闲时周期性地向补数源询问日志头序号并补齐，否则“最后几条事件丢了、之后没有新事件”会永远发现不了。
  * 缺口**一定会出现**，来源包括：leader 在日志提交后、事件发布前崩溃；IPC 背压丢弃；重放阶段不发布。补数方式是读取 Raft 日志录制，用同一份撮合代码确定性重放，重新生成缺失序号区间的事件。
  * **重放终点必须是已提交位置。** 对仍在进行的 term，`RecordingLog` 里记录的提交位置为 0，需读取该成员 ConsensusModule 的 commit-position 计数器；term 已结束时才可用 `RecordingLog` 的值。不能直接用录制末端，leader 的录制里可能含未提交的尾部。
  * **尾部缺口无法被后续事件触发发现**（最后几条丢了、之后没有新事件）。消费端需要周期性地向补数源询问日志头序号并补齐。
  * 补数事件与 leader 当初产生的事件逐字节一致（含时间戳，取日志里记录的集群时间），已由测试验证。
  * **从快照开始重放：** 补数不必每次从日志起点开始。为请求区间 `[from, to]` 选择“最后事件序号小于 `from` 的最新快照”作为引擎种子，再从该快照的日志位置重放到 `to`，重放长度不超过一个快照间隔。没有满足条件的快照时，才要求日志未被裁剪、从起点重放。
  * **日志裁剪的约束：** 只能裁剪最新快照之前的日志（按 segment 边界向下取整），且裁剪前必须已完整归档到 S3。裁剪之后，序号早于“最早可恢复序号”（最早的可用快照之后的第一条事件，或日志起点）的事件无法由集群本地补数，会得到明确的 `EventsUnavailable` 错误并带上最早可恢复序号；这类缺口只能从 S3 归档恢复，属于运维事件而非自动路径。保留的快照数量因此决定了本地补数的回溯窗口。
* **行情旁路：** 委托簿增量与成交行情对延迟敏感，应直接由集群通过 Aeron（UDP 单播/组播）推送到行情网关，不经 Kafka。Kafka 仅用于下游持久化与分析。

## 4. 数据回放与状态投影层 (Materialization & Verification)

### 4.1 流式清算与投影 (CQRS)

* 下游消费者订阅 Kafka，按序号串行回放事件，维护账户余额、订单与成交，并写入 MySQL（用户查询）与 Elasticsearch（多维检索）。生产形态可用 Apache Flink 实现；骨架用等价的普通消费者，逻辑一致：状态是 `lastSeq` + 投影表。
* **恰好一次靠“同一事务”，不靠两阶段提交：** 一批事件的业务写入与 `projection_checkpoint.last_seq` 的更新在同一个 MySQL 事务里提交。事务内先 `SELECT last_seq ... FOR UPDATE`（同时起到防双写者的栅栏作用），`seq <= last_seq` 的事件跳过，`seq != last_seq + 1` 立即回滚并报缺口（由上游补数后重试）。进程崩溃、Kafka 重投、重启后从头消费，都只会得到同一个终态。
* **Kafka offset 不是权威进度：** 权威进度是数据库里的 `last_seq`。offset 提交只是减少重复消费，丢了也不影响正确性。消费者启动时从数据库读取 `last_seq` 作为 `GapFillingConsumer` 的初始状态。
* **投影只依赖事件，不回查撮合内存：** 买方冻结额按“买单限价 × 数量”计算，成交时按成交价结算并退回价格改善，撤单按事件携带的剩余数量释放冻结，与撮合引擎的资金公式一致，因此需要保存订单限价（`orders` 表）。
* **批内合并写入：** 一个批次内先在内存里合并余额增量、订单变化和成交，批末用批量语句一次写入。逐事件执行约 10 条 SQL 时吞吐只有每秒约 2700 个事件，合并后约 15000（批大小 1000）、约 19600（批大小 5000），结果与逐事件应用完全一致（对账与幂等测试验证）。这仍比撮合的产出速度低一个数量级（§5.1），持续高负载下投影会积压。
* **表结构（InnoDB）：** `projection_checkpoint`、`account_balance(account_id, asset)`、`orders`、`trades(seq 为主键)`。余额用增量更新（`INSERT ... ON DUPLICATE KEY UPDATE x = x + ?`）。
* **一致性语义：** 查询侧相对撮合核心存在最终一致窗口（通常几十毫秒到数秒）。API 必须明确约定：下单确认以集群响应为准，历史/资产查询以投影为准。

### 4.2 自动化稽核

* Raft 日志及快照定期归档到 Amazon S3。
* 离线环境以同一份撮合代码**确定性重放**归档日志，输出的账户余额与未成交订单与 MySQL 投影逐账户、逐订单对账，差异即告警。
* **稽核只在命令边界上有意义：** 一条命令会产生多条事件（如 ACCEPTED + TRADE），投影的 checkpoint 可能落在中间，而撮合状态是整条命令处理完之后的。因此对账要求投影已追平日志头（`last_seq` 等于引擎最新事件序号），否则报告“投影滞后”并跳过，不判定为差异。
* 该机制同时验证撮合代码的确定性与投影逻辑的正确性，并可用于发布前的回归验证。

### 4.3 日志归档与裁剪（S3 / MinIO）

**归档对象**（对象键以 `{prefix}` 开头，`{prefix}` 区分集群与成员，如 `cluster-1/member-0`）：

| 对象 | 键 | 说明 |
|------|----|------|
| 日志 segment | `{prefix}/log/{recordingId}/{basePosition:020d}.rec` | 本地 Archive 里**已完成**的 segment 文件，原样上传、不转码 |
| 录制元数据 | `{prefix}/log/{recordingId}/meta.json` | 录制起点 `startPosition`、`segmentFileLength`，首次归档时写入 |
| 撮合快照 | `{prefix}/snapshots/{logPosition:020d}-{lastSeq:020d}.bin` | 引擎状态字节（本项目自有格式，与 Aeron 无关） |

**归档规则**
* 只归档**完全落在已提交位置之内**的 segment（`basePosition + segmentFileLength <= commitPosition`）；活动 segment 不归档，其数据由本地 Archive 提供。
* 完整性：上传时在对象元数据里附 SHA-256；上传后 `stat` 校验大小；读取时重新校验 SHA-256，不符即报错，不静默使用。
* 幂等：同一 segment 重复上传得到相同对象；已存在且大小、哈希一致则跳过。归档进程可随时崩溃重启。
* 多节点：各成员的日志内容一致，但 segment 边界与录制起点可能不同，所以键里带成员号，由固定的一个成员（或 leader 所在节点）负责归档。

**裁剪规则（硬约束，代码里不提供绕过归档的入口）**
* 目标位置 = min(最新快照的日志位置向下取 segment 边界, S3 上从本地起点开始连续归档到的末端)。
* 对 `[本地起点, 目标)` 内每个 segment，必须在 S3 上存在且大小、哈希元数据与本地文件一致；任何一个缺失或不符，拒绝裁剪并说明原因。
* 同一最新快照也必须已归档到 S3，否则拒绝裁剪（否则“快照之前的日志”和“快照”不能一起恢复）。

**读取路径（补数 / 稽核重放）**
* 种子：本地和 S3 上的全部快照里，选最后事件序号小于请求起点的最新者；都没有时要求日志从 0 可读（本地起点或 S3 起点为 0）。
* 日志：`[种子位置, 本地起点)` 从 S3 的 segment 读取，`[本地起点, 提交位置)` 从本地 Archive 重放。S3 对象是 Aeron 原始 term 数据，按 Aeron 帧格式（32 字节头、32 字节对齐、padding 帧、分片重组）顺序解析，与线上日志帧一一对应，之后走同一段命令解码与撮合代码。
* 因此回溯窗口不再受本地裁剪限制，只受 S3 保留策略限制；超出 S3 保留的请求仍然得到 `EventsUnavailableException`。

## 5. 可靠性与运维要求

* **持久性（先持久、再确认）：** Archive 的 `fileSyncLevel` 与 `catalogFileSyncLevel` 默认设为 2（fsync 数据与元数据），Aeron 默认是 0（只写页缓存，进程崩溃不丢，但整机断电会丢“已确认”的订单）。用 `strace` 确认 fsync 确实发生（同样负载下 2 次 → 2664 次）。在本机虚拟磁盘上的代价：限速 2000 命令/s 时确认延迟 p50 0.7ms → 1.0ms、p99 8ms → 20ms；真实磁盘需要重新测，应使用带掉电保护的 NVMe。**单成员集群没有复制，不满足“不能丢”；生产至少 3 个成员，分布在不同故障域。** 尚未做过断电/整机故障测试，fsync 与提交位置的先后关系依据 Aeron 的行为推断，没有做过掉电验证。
* **故障切换：** 骨架中 leader 心跳超时设为 2 秒（Aeron 默认 10 秒），3 成员组 leader 宕机后选主并恢复服务的实测约数秒；生产值需结合网络抖动与 RTO 目标评估，过小会引起误切换。
* **部署：** 每个 Raft 组 3 或 5 节点，跨可用区部署时需评估 Raft 提交延迟预算；同城低延迟与跨城容灾分层设计。
* **背压与保护：** 网关限流、撤单风暴保护、单账户限频、市场级熔断与暂停撮合开关。
* **可观测性：** 端到端延迟（网关 → 提交 → 撮合 → 确认）分位数、日志提交延迟、Kafka 发布滞后、Flink 消费滞后、对账差异数。
* **演练：** 主节点故障切换、快照恢复、整库重建（由 Kafka/S3 重放重建 MySQL）定期演练。

### 5.1 压测结果与容量认识（单机沙箱，仅用于发现问题，不是容量承诺）

环境：4 vCPU / 16GB，撮合集群、网关线程、压测发生器和 MariaDB 都在同一台机器上，驱动用单线程模型。工具见 `exchange/load.sh`。

**1 万个活跃账户 × 3 个网关会话**（开户 2 万笔入金后，限速与不限速两个阶段；**节点默认 fsync，即 `fileSyncLevel=2`**）

| 项目 | 结果 |
|------|------|
| 限速 5000 命令/s × 15s | 下单确认延迟 p50 0.68ms、p99 16.7ms、p99.9 65ms、max 80ms |
| 不限速（窗口 2000/网关） | 30 万命令在约 1.1s 内处理完（约 27 万命令/s），进程 CPU 约 84%；排队延迟 p50 22ms、p99 54ms。只是短脉冲，不是持续吞吐，也不要对虚拟磁盘上的 fsync 成本过度解读 |
| 一致性 | 63.7 万个事件序号连续、无缺口；日志确定性重放 1.2s，状态哈希与线上一致；资产守恒；egress 回报与事件发布均 0 丢弃 |
| 投影到 MariaDB | 63.7 万事件 32s（约 19800 事件/s，批大小 1000）；对账一致。投影优化前同样数据约 2000 事件/s（314s） |

**发现并已修复的问题**
1. **回报被静默丢弃：** 服务端把 `offer` 的所有负值都当背压丢弃，包括发布缓冲 term 轮转时的 `ADMIN_ACTION`（应立即重试）。2 万笔入金丢了 3 条确认，同样的写法在事件 IPC 发布路径上会平白产生事件序号缺口。已改为 `ADMIN_ACTION` 有界重试、真正背压才丢弃，并加了计数与单元测试。
2. **投影吞吐不足：** 见 §4.1，已做批内合并。
3. **`maxConcurrentSessions` 默认 10：** 第 11 个会话就被拒绝，已把节点默认值改为 1000。

**仍未解决的限制**
* **投影仍比撮合慢一个数量级。** 持续满载时积压无上界增长。方向：按账户分片并行投影（每个分片独立 checkpoint）、更大批、事件先落 Kafka 再多消费者并行。需要单独设计，因为单一 `last_seq` checkpoint 是目前的幂等机制。
* **1 万个原始集群会话不可行：** 单线程驱动下约 550 个会话后连接开始超时，随后客户端因驱动 keepalive 超时崩溃；专用线程驱动约 1800 个会话（建立 319s，平均 176ms/会话，且持续恶化）后同样失败。结论是必须走网关复用。
* egress 在客户端消费慢、或突发时会丢回报，网关必须按 §1 处理超时与重试。
* 压测没有覆盖：多节点集群下的负载、长时间稳定性（浸泡）、GC 暂停影响、跨机网络、磁盘 fsync 策略对延迟的影响。

### 5.2 “不能丢”清单（逐环节审计）

| 环节 | 丢失风险 | 处理 | 验证 |
|------|----------|------|------|
| 日志落盘 | Aeron 默认只写页缓存，整机断电丢“已确认”订单 | `fileSyncLevel=2`、`catalogFileSyncLevel=2` 为节点默认 | `strace`：fsync 调用 2 次 → 2664 次；**没有做断电测试** |
| 命令发往已宕机 leader | 写进其发布缓冲后丢失 | 客户端超时重试，状态机幂等（下单/撤单/入金） | `FailoverTest`、引擎幂等测试 |
| **重试导致重复** | 入金重试会重复入账（钱） | 入金必须带 `depositId`，重试返回原结果；没有键的入金被拒绝 | `retryOfDepositIsIdempotent...` |
| egress 回报 | 背压时被丢（为避免慢客户端拖住撮合） | 允许丢，但重试能取回原结果（订单号/拒绝原因/撤单剩余量/入金金额）；丢弃有计数 | 引擎层 5 个“重试返回原结果”测试 |
| 事件发布缓冲背压 | 撮合线程立即丢弃事件 | 有界等待（默认 3s，期间维持服务心跳），超时进降级窗口并丢弃，由日志补回 | 下游卡 2.5s：等待 8 次、0 丢弃；下游死亡：丢 2745 条、日志补回 3001/3001，且只用 0.2s |
| 事件发布线程 | 下游异常使线程静默退出 | 按批发送并 flush 确认，失败对同一批退避重试，线程不退出 | 注入 flush 失败，全部送达；变异（不重试）该测试失败 |
| Kafka 发送 | 异步发送失败无人知晓；生产者放弃重试 | 无限重试 + 无限超时；每条带回调，失败在 flush 抛出 | `MockProducer` 注入失败；变异（吞掉回调）失败 |
| 消费端缺口检测 | 只在收到新事件时检查，尾部缺口永远发现不了 | 空闲时定时向补数源问日志头并补齐 | 尾部丢 25 条、无后续事件，仍补齐；变异失败 |
| 投影写库失败 | 复位时读 checkpoint 也失败 → 留下陈旧消费者，宕机恢复后无后续事件则永久落后 | 复位改为惰性，失败保持“待重建”；运行循环不因异常退出 | 宕机持续到事件流结束仍补齐；变异下数据库永远停在 300/1000 |
| 日志裁剪 | 本地删了而归档没有 | 唯一入口 `LogTrimmer`，重新下载比对内容后才删 | 见 §4.3 |

**仍然存在的缺口（需要明确承担或继续解决）**
* **没有做过断电/整机故障测试；单成员集群没有复制，不满足“不能丢”。** 生产至少 3 个成员、不同故障域，并带掉电保护的磁盘。fsync 与提交位置先后关系依据 Aeron 行为推断，未验证。
* **Kafka 与 MySQL 自身的持久性依赖它们的配置，本骨架没有覆盖：** Kafka 需要 `replication.factor>=3`、`min.insync.replicas>=2`、禁止 unclean leader election；MySQL 需要 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`。
* **幂等结果集合只增不减**（下单/撤单/入金各一份）。给它们加过期窗口会破坏“重试能取回原结果”的保证：过期后的重试会被当成新请求。过期窗口必须大于网关重试窗口，并且需要显式协议（过期后的重试必须被拒绝，而不是重新执行）。目前没有过期，所以内存无界。
* **撤单的重试只在“已撤销”时可取回原结果**；被全部成交而消失的订单，重复撤单得到“未知订单”，无法区分“从未存在”和“已成交”，要靠事件流/投影查询确认。
* 撮合线程等待背压期间若超过 Aeron 的服务心跳超时会被判定失联；本骨架只测到单次等待约 2.5s，没有验证上限，默认等待上限 3s 是保守值。
* 发布线程关闭时，手里尚未确认的一批事件会留在内存里丢失，只能靠补数找回。
* 补数本身依赖补数源（成员 Archive 或 S3）可用；两者都不可用时缺口只能等待。
* 网关（压测里的 `Gateway`）只判定“回报丢失”，没有实现“超时后用同一 `clientOrderId` 重试”；真实网关必须实现。

### 5.3 “不能出错”清单（fail-stop 审计）

| 环节 | 可能“带病运行”的方式 | 处理 | 验证 |
|------|----------------------|------|------|
| 状态机抛异常 | Agrona 的 AgentRunner 只记录异常、继续下一轮：该命令的日志位置已前移，状态可能只改了一半，所有副本还会一起错 | 服务回调内捕获 `Throwable`，一律 fail-stop（默认 halt JVM，共识模块随之退出） | 实测旧行为：命令 3 被吞、命令 4-6 照常处理；现在整个节点停止，重启后重放**正确应用命令 3**（停机不丢）；变异（吞异常）测试失败 |
| 算术溢出 / 余额变负 | 结算处用未受检的乘加，溢出会静默回绕 | 总供应量上限（入金超限在改状态前拒绝）+ 全部受检算术 + 每次余额变更检查非负 + 全量不变量（守恒、非负、冻结额必须等于在簿订单所需）在快照前/加载后检查 | 极值测试、人为篡改后被发现、随机流每 500 步全量检查；两个变异测试失败 |
| 快照损坏或版本不符 | 解析出一份“看起来合法”的错误状态 | 快照带魔数、版本、SHA-256，不合格拒绝加载；状态太大数组放不下时明确失败而不是整数溢出 | 任意字节翻转、截断、错误版本均被拒；变异（不校验）失败 |
| 磁盘静默位翻转 | **实测：关掉校验时，翻转日志里一个比特，节点重启后照常服务、没有任何报错，状态已被悄悄改变** | Archive 录制/重放启用 CRC32C | 启用后重启在该帧报 `CRC checksum mismatch` 并拒绝服务；变异（不启用）测试失败 |
| 状态机版本 | 用新逻辑加载旧状态 | 显式 `appVersion`（`1.0.0`），Aeron 拒绝不兼容的快照 | 升 major 后重启报 `incompatible version` 且不服务。**只覆盖快照加载，纯日志恢复没有版本记录**，由下一行覆盖 |
| 副本分歧 / 代码语义变化 / 非确定性 | 字节没变、校验和通过，但结果不同；没有任何机制会发现 | **链式哈希检查点**：状态机对全部输出事件维护 64 位链式哈希，每 1000 个事件把（序号, 哈希）作为服务消息写入 Raft 日志；任何重放（重启、follower、补数）到达该点必须算出同一个值，否则 fail-stop。服务消息的 `session` 恒为 `null`，客户端伪造不了 | 新语义重放旧日志在第一个检查点 fail-stop；分歧的副本自己停下、另外两个继续正确服务；伪造的检查点被当畸形命令拒绝；重放路径也核对检查点，且不会因检查点消息产生多余事件（曾经会，已修复并有测试）；3 个变异测试失败 |
| 投影写错 | 重试无法修复的不自洽数据被一直重试或写入 | 表带 CHECK（余额非负、订单剩余量合法、价格数量为正）；约束违反与未知事件类型是**不可重试**错误，运行循环停止并保留原因，不提交 offset | 不自洽的批次整批回滚、循环自己停止且只失败一次；变异（去掉约束）失败 |

**这轮发现并修复的、由新防护引入或暴露的问题**
* 重放（补数/对账/重建状态）曾把日志里的检查点消息当命令交给引擎，会产生多余的“畸形命令”事件并让事件序号与线上错位。
* 新加的 CHECK 约束与批量 `INSERT ... ON DUPLICATE KEY UPDATE` 冲突：数据库先对“插入元组”做检查，而增量常常是负的。改为先 `INSERT IGNORE` 零行再 `UPDATE` 加增量，投影吞吐约 15400 → 14300 事件/s。

**仍然存在的缺口**
* **检测有延迟窗口：** 检查点每 1000 个事件一次，内存损坏或分歧最多在这之后才被发现；这期间 leader 可能已经向客户端和下游发出了错误的回报/事件。检查点不能做“发布前校验”。
* **日志里只有 leader 的哈希：** 如果 leader 自己是分歧的一方，正确的 follower 会被判为“分歧”而停机，整体不可用但不会对外提交新的错误；需要外部监控（比较各成员的链式哈希、与 S3 重放的结果）来判断谁是对的。
* 检查点只覆盖输出事件序列；不影响输出的内存状态（比如幂等结果集合）损坏要等快照前的全量检查才发现。全量检查是 O(状态)，不在热路径上；热路径上只有“每次余额变更非负”。无 ECC 的内存位翻转没有别的防线。
* 下游消费者（投影等）不核对链式哈希，事件在 Kafka 里被破坏时只有数据库 CHECK 兜底；可以让 leader 把检查点也作为事件发布，供消费端核对（未做）。
* 快照之前发出、之后才到达的检查点无法核对（计入 `checkpointsUnverifiable`，不算通过）。
* “毒命令”（由日志确定性触发的停机）重启后会再次触发，这是预期行为，不能自动跳过；没有提供运维流程和工具，也没有停机告警。单节点部署下 fail-stop 等于整个服务不可用。
* `Runtime.halt` 不执行关闭钩子：事件发布线程手里未确认的一批会丢，靠补数找回。
* CRC32C 与检查点的性能开销没有单独测量；上面的投影吞吐是唯一重新量过的数字。
* Aeron 冷启动选举默认要等 60 秒“启动探查”才会在缺席成员的情况下用多数派选主，且该值必须是 leader 心跳超时的整数倍，运维需要知道。

7. 补数的生产形态：缓存引擎状态以避免重复重放；S3 保留策略、加密、跨区复制与生命周期规则的具体取值。

## 8. 骨架实现状态与已知限制

代码位于 `exchange/`（Maven，Java 21，Aeron 1.54.0，Kafka client 3.9.0）。`mvn test` 运行全部测试（含真实 MariaDB 进程，首次运行需下载其二进制），`./run.sh` 运行演示。

**已实现并有测试覆盖**
* Aeron Cluster（1 或 3 成员 Raft 组）：MediaDriver + Archive + ConsensusModule + 撮合 `ClusteredService`。
* 确定性撮合引擎：限价 GTC、价格-时间优先、成交价取 maker 价、买方价格改善退款、撮合前冻结资金、`clientOrderId` 幂等去重、溢出检查。
* 属性测试：随机命令流下资产守恒；两个引擎重放事件流和状态哈希完全一致；中途快照恢复后继续一致。
* 单节点集成测试：事件序号连续、重启后日志重放恢复、快照恢复（断言确实从快照启动）。
* **3 节点故障切换**：leader 宕机后选主；客户端超时重试后继续服务；已提交的挂单不丢；三个副本状态哈希一致；旧 leader 重启后从自己的日志恢复并追平。
* **补数**：`LogReplayer` 读取 Archive 中的 Raft 日志，确定性重放生成任意序号区间的事件；`GapFillingConsumer` 作为下游参考实现，保存 `lastSeq`、丢弃重复、遇缺口调用补数、周期性追平日志头。测试覆盖头部/中间/尾部缺口，以及“leader 提交后、发布前崩溃”的真实切换场景，补回的事件与 leader 当时产生的逐字节一致。
* **MySQL 投影（`projection/`）**：`JdbcProjector` 在同一事务里写业务表与 `last_seq`，`SELECT ... FOR UPDATE` 锁 checkpoint；重复跳过、缺口回滚。`ProjectionPipeline` 串起补缺口去重与批量写库，写库失败即复位并从数据库 `last_seq` 重来；`KafkaProjectionRunner` 先落库再提交 offset；`ProjectionAuditor` 把投影与日志重放得到的撮合状态逐账户、逐订单对账。测试在真实 MariaDB 11.4 上覆盖：随机流投影与引擎一致且资产守恒、重复/重叠批次得到相同终态、批内崩溃整批回滚、缺口拒绝、4 个并发写入者终态一致、对账能发现被篡改的余额和丢失的订单、Kafka 重投被吸收；并做过变异验证（去掉价格改善退款，对账立即报差异）。全链路测试：真实集群 + 人为丢事件 + 补数 + 写库 + 对账一致。
* **补数从快照开始重放**：`LogReplayer` 读取 `RecordingLog` 里的全部有效快照（不能用 `RecoveryPlan`，它只含最新一份），选最后事件序号小于请求起点的最新快照做种子，再从该快照的日志位置重放；没有可用快照时回退到日志起点。日志裁剪见下一条（必须先归档）。测试覆盖：种子选择（快照后/快照前/恰在快照边界）、日志头状态与线上服务逐字节一致、没有对象存储时裁剪后更早的请求得到带“最早可恢复序号”的 `EventsUnavailableException`。快照分块加了魔数（`SnapshotFraming`），因为 Archive 里的快照录制夹有集群自己的标记帧。
* **S3/MinIO 归档与受保护的裁剪（`archive/`）**：`LogArchiver` 把本地已完成且已提交的 segment（原样）与撮合快照上传到 MinIO，附 SHA-256、上传后校验、可重复执行（第二次不再上传）；`LogTrimmer` 是裁剪日志的唯一入口，目标取 min(最新快照所在 segment 边界, 对象存储连续归档末端)，最新快照必须已归档，并对每个待删 segment **重新下载比对内容**，任何缺失或不一致都拒绝。`LogReplayer` 接上 `ArchiveCatalog` 后，本地已裁剪的日志从对象存储读取（Aeron 原始 term 数据，按帧解析、分片重组）、与本地 Archive 重放拼接，本地快照丢失时降级为对象存储里的快照。真实 MinIO（从源码编译，官方二进制已下架）上的测试覆盖：未归档即裁剪被拒；归档幂等；对象存储里的 segment 与本地逐字节相同；裁剪后只有本地数据时早期事件不可补，接上对象存储后同样请求能补且与 leader 当时的事件逐字节一致，含跨对象存储/本地接缝的区间；本地快照录制被删后改用 S3 快照；整个日志重建的状态哈希与线上一致；集群从被裁剪的日志 + 快照重启并接续事件序号；对象存储缺一个 segment 时裁剪停在缺口之前；对象内容被翻转一个字节时拒绝裁剪、读取侧报校验错误（并做过变异验证：去掉内容比对，该测试立即失败）；最新快照缺失时拒绝裁剪。
* **fail-stop 与完整性防护：** 服务回调 fail-stop、受检算术与全量不变量、带校验的快照、Archive CRC32C、`appVersion`、链式哈希检查点（含重放路径核对）、投影 CHECK 约束与不可重试错误；每一项都有真实触发的测试和变异验证，缺口见 §5.3。
* **压测工具**（`exchange/load.sh`）：1 万活跃账户经网关会话复用的并发压测（限速/饱和两阶段，延迟分位数，全量一致性校验与投影对账）、原始会话风暴、投影吞吐基准；结果见 §5.1。
* 事件出口：Aeron IPC → 独立发布线程 → `EventSink`（Kafka 幂等 Producer 或日志）；Kafka 路径仅用 `MockProducer` 验证，未连真实 broker。
* 请求方确认：leader 通过 egress 把 ACCEPTED/REJECTED/CANCELLED/TRADE 回写给下单会话。

**与目标设计的差距（骨架有意不做）**
* 编码为手写定长布局，非 SBE。
* 仅单市场：无 Multi-Raft、无跨分片资金方案（§2.2）。3 个成员都在同一台机器、同一 JVM 内，没有真实网络分区、跨可用区延迟、磁盘故障的验证。
* 仅限价 GTC：无市价、IOC/FOK、自成交保护、手续费、最小价格/数量单位校验。
* 撤单在同价位队列中线性查找（O(n)），生产需要侵入式链表。
* 补数每次都重新读取快照并重放，未缓存引擎状态；归档对象的读取是整段下载到内存（segment 默认 128MB，生产需要流式读取）。
* 归档进程需要与节点同机读取 Archive 目录（sidecar），并且需要外部调度（周期性调用 `archiveOnce` 与 `trim`）；骨架没有调度、没有归档滞后告警，也没有 S3 保留策略、加密、跨区复制。多节点只验证了单成员归档，没有验证“固定一个成员负责归档”的切换。
* 补数读取不覆盖“分片消息恰好跨在对象存储/本地接缝上”的情况（检测到会报错）；当前日志消息都远小于 MTU，不会分片。
* 运维约束：归档 `segmentFileLength` 不能小于日志 term 长度（Aeron 会把它抬到 term 长度），裁剪只能按 segment 整段进行，所以快照间隔、term 长度和保留窗口要一起规划。测试把日志 term 缩到 64KB 以便几千条命令就能跨 segment。
* 投影用普通消费者实现，未做成 Flink 作业；Elasticsearch 投影、离线稽核的定时流水线、行情 UDP 旁路未实现。投影在 MariaDB 上验证，未在 MySQL 官方发行版上跑过（SQL 使用两者共有的语法）。
* 投影写入是单线程串行（一个 checkpoint 行），吞吐上限未压测；分库分表或按账户并行需要另行设计 checkpoint 方案。
* 对账只在投影追平日志头时有意义，尚无“截至某个命令边界”的对账。
* 事件发布进程内的去重器重启后状态清零（原因见 §3），只作尽力过滤；真正的去重与缺口检测在消费端。
* `clientOrderId` 去重集合只增不减（见 §7 第 5 项）。
